# Stack Profile — SDLC Control Plane

Row names follow [`stack-template.md`](stack-template.md) exactly, because the pipeline
dispatches on them: `.github/prompts/run-task.prompt.md` looks up "the stack profile's
**Affected lint/test/build** command" and "**Access control**" by name. A row under a
different name is a row no phase can find. Rows beyond the template's are this workspace's own
and no phase reads them.

Some rows read **Not selected**. Those apply to this stack and simply have not been decided;
each names who decides. That is deliberately not `N/A`, which tells the pipeline the check does
not apply and to skip it — skipping is the wrong answer for a decision that is merely
outstanding.

| Access control           | Database layer, per [ADR-0002](../adr/0002-append-only-evidence-envelope-log.md) — Accepted, built by task 2.2 in `packages/evidence-store/migrations/0001-evidence-envelope.sql` and proven role by role on PostgreSQL 16 by `packages/evidence-store/src/database-roles.integration.mjs`, whose grants snapshot is the executable copy of this row. Four roles: `evidence_owner` owns every object and is used only by `migrate`; it has given up `DELETE` and `TRUNCATE` on `evidence_envelope` and `UPDATE`, `DELETE` and `TRUNCATE` on `evidence_redaction`, keeping `UPDATE` on the envelope because the redaction's foreign-key check needs it. `evidence_app`, the service, holds `SELECT` on `evidence_envelope` and `INSERT` on its `envelope_version`, `workspace_id`, `change_id`, `policy_id`, `submitted_by` and `evidence` only - never `received_at` or `redacted_at`, which the database stamps - `SELECT` on `schema_migrations`, and owns nothing. `evidence_retention` holds `SELECT (id, received_at, redacted_at)` and `UPDATE (evidence, submitted_by, redacted_at)`. `evidence_audit` holds `SELECT` on every envelope column except `evidence`, and on `evidence_redaction`. `PUBLIC` holds nothing, `CONNECT` on the database included. The control is the `BEFORE UPDATE` trigger, `SECURITY DEFINER` and owned by `evidence_owner`: the only update it admits is a redaction - payload to `NULL`, the four `submitted_by` names to `null`, `redacted_at` stamped by the database, every identity column and the seven identifiers kept - it writes the `evidence_redaction` row itself, naming `session_user`, and refuses any update to a tombstone. Column grants narrow; the trigger decides values. **Who can read evidence at rest**: `evidence_app` (it serves the indicators) and `evidence_owner` (it owns the table); neither `evidence_retention` nor `evidence_audit`. No row-level security: one application role serves every workspace, so a policy keyed on a setting the application itself sets would be a convention the application controls, not a boundary; tenant isolation is ADR-0003's seam predicate plus `list({ workspace_id })`. The service refuses to start (`role-unsafe`) as a role that is a superuser or has `CREATEROLE`, `CREATEDB`, `REPLICATION` or `BYPASSRLS`; is a member of any other role (privilege checks do not count a `NOINHERIT` role's memberships, yet it can `SET ROLE` to each of them); owns the database or anything in the `evidence` schema; holds `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES` or `TRIGGER` on `evidence_envelope`, any write on `evidence_redaction`, or `INSERT` on `received_at` or `redacted_at`; or cannot insert a payload and read the log. It reads the catalog once, at startup: a grant made while the service runs is seen at the next start. **Requirements on whoever selects the deploy target, not properties of this system**: a cluster superuser, or a managed service's administrator, can read and rewrite everything; `evidence_owner` can disable the trigger or re-grant itself `DELETE` (a catalogued act the grants snapshot catches when it runs, not when it happens); the trigger checks the form of a redaction, not the row's age, so whoever holds the `evidence_retention` credential can redact every live payload at once, irreversibly though each leaves an `evidence_redaction` row - holding redaction to the 90-day window is task 2.5's; backups, replicas and operator copies hold INTERNAL evidence no code here controls; custody of the four roles' credentials, and who on the host can read `PGPASSWORD`, are the deployment's. At the port layer the equivalent is that the store exposes `append`, `list` and `listRecords` and no method that can remove or rewrite a record, which the conformance suite asserts |

| Data access              | Raw, parameterised SQL in one adapter module, `packages/evidence-store/src/postgres-store.mjs`, through postgres.js 3.4.9: every value is a bound parameter of a tagged template, and jsonb is bound as text and cast (`${text}::text::jsonb`), because a string bound straight to jsonb is stored as a string scalar. No query builder, no ORM. The driver's raw-text entry point (`sql.unsafe`) is used only by `migrate.mjs`, to execute the bundled migration files, and by test code; `postgres-store.test.mjs` fails if the adapter calls it or the identifier helper. Every driver option is passed explicitly by `database-config.mjs`, so no environment variable changes TLS, pooling, statement preparation or debug output. A driver error is never logged or answered: the adapter turns it into `EvidenceStoreFault`, answered 503, and cancels any statement not answered in 5000 ms (a literal). Prepared statements (`prepare: true`) do not survive a transaction-pooling proxy in front of the server: a deploy-target constraint | Migrations + verify      | Plain numbered SQL files, `packages/evidence-store/migrations/NNNN-slug.sql`, applied in order by the in-repo runner `packages/evidence-store/src/migrate.mjs`, each in one transaction with its `evidence.schema_migrations` row (version, name, SHA-256 checksum, `applied_at`, `applied_by`) under an advisory lock, so a failed migration rolls back whole. An applied file whose bytes changed, an applied version with no file, an unknown file or a gap stops the runner. Every SQL file's first line names the one role it runs as. Two stages: `pnpm nx run evidence-store:bootstrap --database <name>` as a cluster administrator, once - the four roles, created without passwords, which the operator sets out of band, and the database owned by `evidence_owner`; then `pnpm nx run evidence-store:migrate` as `evidence_owner`, the only role the runner accepts (a superuser is refused). `node packages/evidence-store/src/migrate.mjs status` reports applied and pending versions. The service never migrates: it refuses to start unless what is applied is exactly what it bundles. No down-migrations: the log is append-only, and a wrong migration is corrected by the next one. **Verify**: `pnpm test:integration` migrates an empty database and runs the conformance suite, the role and trigger tests, the grants snapshot and the audit queries against it
