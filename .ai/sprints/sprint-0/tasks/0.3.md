## Design Decisions

- The policy evaluator separates two failure modes: malformed evidence or an unsupported policy version is `rejected`; well-formed evidence failing a rule is `needs-remediation`. Bad input and a real finding are different events and a workspace has to be able to tell them apart.
- `disposition` is a technical verdict and the output carries `policy_id` back to the approving decision reference — the evaluator never emits an approval, a score, or a recommendation.
- The indicator payload carries its own disclaimer field stating it is a descriptive engineering indicator, not a portfolio decision or compliance conclusion. Putting it in the response means it travels with the data instead of living only in the docs.
- The registry throws on an invalid registration and on a duplicate `workspace_id`; a silently dropped workspace is an invisible governance gap. Entries are frozen so a caller cannot mutate registry state through a returned reference.
- The registry sorts `list()` by `workspace_id` for deterministic API responses (FR-1.1's third criterion).
- Indicators ignore an unrecognised tier rather than throwing — a reporting path must not break on a record the schema tolerates.
